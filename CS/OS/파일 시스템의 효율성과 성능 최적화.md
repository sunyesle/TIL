# 파일 시스템의 효율성과 성능 최적화

## 효율성

- Unix는 파일이 생성되기 전에 inode를 미리 할당하므로, 파일이 없어도 inode 저장 공간을 차지한다. 또한 inode를 디스크에 분산 배치하고 관련 데이터 블록을 가까이 저장하여 디스크 탐색 시간을 줄인다.
- 일부 시스템은 파일 크기에 따라 클러스터 크기를 다르게 사용하여 작은 파일의 저장 공간 낭비를 줄이거나 큰 파일의 접근 효율을 높인다.
- 마지막 접근 시간 등의 메타데이터 갱신을 줄이거나 지연하면 불필요한 디스크 쓰기를 줄일 수 있다.
- 주소 크기가 커지면 더 넓은 저장 공간을 표현할 수 있지만, 포인터 저장 공간도 증가하므로 주소 범위와 저장 공간 효율을 함께 고려해야 한다.
- 고정 크기 테이블 대신 동적 할당을 사용하면 필요한 만큼 메모리를 할당하여 메모리 낭비를 줄이고 시스템 상황에 유연하게 대응할 수 있다. 단, 동적 할당은 관리 알고리즘을 복잡하게 만들 수 있다.

## 성능

### 캐싱(Caching)

- **디스크 컨트롤러 캐시**: 디스크에서 특정 섹터를 요청하면 해당 트랙의 데이터를 함께 읽고, 요청하지 않은 트랙의 데이터도 컨트롤러 내부에 캐싱하여 이후 접근 시간을 줄인다.
- **버퍼 캐시 (Buffer Cache)**: 운영체제가 다시 사용할 가능성이 있는 디스크 블록을 메모리에 저장하여 디스크 접근을 줄인다.
- **페이지 캐시 (Page Cache)**: 가상 메모리 시스템과 연계하여 파일 데이터를 페이지 단위로 캐싱한다. 파일 데이터가 메모리 페이지로 관리되므로 디스크 블록 주소와 메모리 주소 간의 변환 부담을 줄일 수 있다.
- **통합 버퍼 캐시 (Unified Buffer Cache)**: 일반 파일 I/O 캐시와 메모리 매핑 파일의 페이지 캐시를 통합하여, 동일한 파일 데이터가 여러 캐시에 중복 저장되는 것을 방지하고 캐시 간 데이터 불일치 문제를 방지한다.

통합 캐시를 사용하는 경우 프로세스 페이지와 파일 페이지가 메모리를 공유하므로, 어떤 페이지를 교체할지 각 페이지 범주에 얼마나 많은 페이지를 보장할지 결정해야 한다.
예를 들어 Solaris에서는 프로세스 페이지에 파일 I/O 페이지보다 높은 우선순위를 부여하면서 어느 한쪽이 메모리를 독점하지 못하도록 제한을 두었다.

### 페이지 교체 정책

파일의 접근 방식은 최적의 페이지 교체 정책에 영향을 미칠 수 있다.
예를 들어 순차 접근 파일에서는 이미 읽은 페이지를 다시 사용할 가능성이 낮고 다음 페이지를 사용할 가능성이 높으므로, LRU 대신 특수한 페이지 교체 정책을 적용할 수 있다.

- **Free-behind**: 순차적으로 파일을 읽을 때 다음 페이지를 요청하면 이전 페이지를 메모리에서 해제하여 메모리 사용을 줄인다.
- **Read-ahead**: 요청한 페이지와 이후 페이지들을 미리 읽어 두어 다음 페이지 접근 시 발생하는 지연을 줄인다.

### 동기 쓰기와 비동기 쓰기

- **동기 쓰기**(Synchronous Write): 쓰기 요청을 동기적으로 처리하며, 기록 순서와 완료 시점의 보장이 중요한 경우에 사용한다. 메타데이터 기록이나 특정 순서가 필요한 데이터베이스 작업 등에 활용된다.
- **비동기 쓰기**(Asynchronous Write): 데이터를 캐시에 저장한 뒤 디스크에 기록한다. 디스크 서브시스템이 쓰기 순서를 효율적으로 조정하여 디스크 헤드 이동과 탐색 시간을 줄일 수 있다.

### 읽기와 쓰기의 성능 차이

캐싱과 비동기 쓰기는 여러 쓰기 요청을 효율적으로 처리할 수 있게 하므로 디스크 쓰기 성능을 높인다. 반면 읽기는 요청한 데이터가 준비되어야 하므로 쓰기보다 처리 순서를 유연하게 조정하기 어렵다. 따라서 시스템 환경에 따라 디스크 쓰기가 읽기보다 빠를 수도 있다.

# 가상 메모리의 기타 고려 사항
## 프리페이징(Prepaging)
**프리페이징**은 프로세스가 실제로 필요로 하기 이전에 필요한 페이지들을 미리 예측하여 메모리에 올려놓는 기법이다.

초기 페이지 부재율을 낮추고 실행 속도를 향상시킬 수 있지만, 예측이 틀릴 경우 불필요한 I/O 오버헤드가 발생하고 메모리가 낭비될 수 있다.

## 페이지 크기
페이지 크기는 메모리 단편화, 페이지 테이블 크기, TLB 효율성에 영향을 미친다.

| 항목 | 큰 페이지 | 작은 페이지 |
|---|---|---|
| **내부 단편화** | 증가 (남는 메모리 공간이 커짐) | 감소 (메모리 낭비가 적어짐) |
| **페이지 테이블 크기** | 감소 (관리할 페이지 수가 적음) | 증가 (관리할 페이지 수가 많음) |
| **주소 변환/매핑 속도** | 빠름 | 느림 |
| **디스크 I/O 효율** | 높음 (한 번에 많은 데이터 이동) | 낮음 (디스크 접근 횟수 증가) |
| **메모리 적재 효율** | 낮음 (불필요한 데이터도 함께 적재) | 높음 (필요한 데이터만 정밀하게 적재) |

## TLB 도달 범위(TLB Reach)
**TLB 도달 범위**란 TLB로 접근할 수 있는 메모리 공간의 크기를 말한다.

```
TLB 도달 범위 = (TLB 엔트리 수) * (페이지 크기)
```

TLB 도달 범위가 넓을수록 더 많은 메모리 영역의 주소 변환 정보를 TLB에 유지할 수 있다. 따라서 요청한 주소의 변환 정보가 TLB에 존재할 확률이 높아져 TLB 적중률을 높일 수 있다.

TLB의 용량은 제한적이므로 TLB 도달 범위를 늘리기 위한 현실적인 해결책은 페이지 크기를 늘리는 것이다. 하지만 페이지의 크기가 커질수록 내부 단편화로 인한 메모리 낭비가 증가할 수 있다.

## Huge Pages
**Huge Pages**는 일반적인 페이지보다 훨씬 큰 크기의 페이지를 사용하는 기술이다.

리눅스에서는 기본 페이지 크기인 4KB 외에도 2MB, 1GB 크기의 페이지를 사용할 수 있다.

페이지 크기가 커지면 하나의 TLB 엔트리가 더 넓은 메모리 영역을 커버할 수 있다. 이는 데이터베이스 버퍼 풀, 가상 머신(VM) 메모리처럼 대규모 메모리를 사용하는 워크로드에서 TLB 미스를 줄이는 데 도움이 된다.

## 프로그램 구조
프로그램이 메모리 참조의 지역성(Locality)을 잘 활용하도록 구조화하면 페이징 성능을 향상시킬 수 있다.

예를 들어 32비트 정수로 이루어진 1024 x 1024 크기의 2차원 배열이 있다고 하자. C언어에서 배열은 행 우선 방식으로 저장되므로 배열의 한 행은 하나의 페이지에 저장된다.

만약 배열의 모든 요소에 접근할 때 외부 루프에서 행을 증가시키고 내부 루프에서 열을 증가시키면, 하나의 페이지에 저장된 요소들을 연속적으로 접근하게 된다. 따라서 한 페이지를 모두 처리한 후 다음 페이지로 이동하므로 페이지 부재 발생을 최소화할 수 있다. (페이지 부재 약 1024회)

반대로 외부 루프에서 열을 증가시키고 내부 루프에서 행을 증가시키면, 연속된 메모리 위치가 아닌 서로 다른 페이지의 요소에 번갈아 접근하게 된다. 메모리에 충분한 페이지 프레임이 없다면 페이지가 계속 교체되면서 거의 매 접근마다 페이지 부재가 발생할 수 있다. (페이지 부재 약 1024^2회)

## 페이지 잠금(Page Locking)
**페이지 잠금**은 특정 페이지를 메모리에 고정하여 디스크로 내보내지 않도록 강제하는 기법이다.

다음과 같은 상황에서 페이지 잠금이 사용된다.

- 운영체제의 핵심 인터럽트 처리 루틴이나 메모리 관리 코드는 항상 메모리에 상주해야 한다.
- I/O 컨트롤러가 메모리에 직접 접근하는 동안 해당 페이지를 내보내면, I/O 작업이 잘못된 메모리 영역을 대상으로 수행되어 데이터가 오염되거나 손실될 수 있다.
